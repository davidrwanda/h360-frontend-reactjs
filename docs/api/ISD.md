## Standard Request Envelope

**Every** H360 API request with a body (POST, PUT, PATCH) follows this structure:

```json
{
  "data": {},
  "meta": {},
  "extras": {}
}
```

### Structure

| Layer | Purpose | Examples |
|-------|---------|---------|
| `data` | **Domain payload** — the resource fields the client is creating or updating | `{ "name": "Diana Clinic", "phone": "+250788123456" }` |
| `meta` | **Operational context** — tracing, idempotency, caller identity for integrations | `message_id`, `correlation_id`, `idempotency_key`, `source_system` |
| `extras` | **Optional hints** — additional context that doesn't belong in the domain payload | Preferred language, callback URL, dry-run flag |

### Request `meta` fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `message_id` | UUID | **Yes** | Unique ID for this specific request. Generated by the caller. Echoed back in the response `meta` for end-to-end tracing. |
| `correlation_id` | UUID | No | Groups related requests across a workflow (e.g., onboarding steps 1–7 share one `correlation_id`). If omitted, server sets it to `message_id`. |
| `idempotency_key` | string | No | Prevents duplicate processing. Server returns cached response for repeated keys within 24h. Recommended for all POST mutations. |
| `source_system` | string | No | Identifier of the calling system (e.g., `h360-web`, `h360-mobile`, `partner-emr`, `fhir-gateway`). Used for audit trail and analytics. |
| `locale` | string | No | Preferred response language (`en`, `fr`, `rw`). Overrides `Accept-Language` header. Default: `en`. |
| `timestamp` | ISO 8601 | No | Client-side timestamp. Useful for offline-first sync and latency measurement. |

### Full request example

```json
{
  "data": {
    "name": "Rwanda Health Group",
    "type": "multi_branch",
    "contact_email": "admin@rwandahealth.rw",
    "contact_phone": "+250788000000"
  },
  "meta": {
    "message_id": "msg_a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "correlation_id": "corr_onboarding-session-xyz",
    "idempotency_key": "idem_create-org-20260226-001",
    "source_system": "h360-web",
    "locale": "en",
    "timestamp": "2026-02-26T09:59:58Z"
  },
  "extras": {}
}
```

### Response echoes request tracing

The server **always** echoes `message_id` and `correlation_id` in the response `meta`:

```
Request  meta.message_id: "msg_a1b2c3d4..."
         meta.correlation_id: "corr_onboarding-session-xyz"
                    ↓
Response meta.request_id: "req_server-generated"       ← server's own ID
         meta.message_id: "msg_a1b2c3d4..."            ← echoed from request
         meta.correlation_id: "corr_onboarding-session-xyz" ← echoed from request
```

This creates a **complete trace chain**:

```
Client App  →  H360 API  →  Partner EMR  →  FHIR Gateway
   msg_001       req_abc       msg_002        msg_003
      └── correlation_id: "corr_xyz" (same across all) ──┘
```

### GET requests (no body)

For GET requests, tracing fields are sent as **headers** instead:

| Header | Maps to | Example |
|--------|---------|---------|
| `X-Message-ID` | `meta.message_id` | `msg_a1b2c3d4...` |
| `X-Correlation-ID` | `meta.correlation_id` | `corr_session-xyz` |
| `X-Source-System` | `meta.source_system` | `h360-web` |
| `Accept-Language` | `meta.locale` | `en`, `fr`, `rw` |

```
GET /api/organizations/uuid-123
Authorization: Bearer <token>
X-Message-ID: msg_a1b2c3d4-e5f6-7890-abcd-ef1234567890
X-Correlation-ID: corr_session-xyz
X-Source-System: h360-web
Accept-Language: fr
```

The response still wraps everything in the standard envelope with both IDs echoed.

### Backwards compatibility

If a client sends a **flat body** (no envelope), the server treats the entire body as `data` and auto-generates `meta`:

```json
// Client sends (legacy / simple)
{
  "name": "Diana Clinic",
  "phone": "+250788123456"
}

// Server interprets as
{
  "data": { "name": "Diana Clinic", "phone": "+250788123456" },
  "meta": { "message_id": "auto-generated-uuid" },
  "extras": {}
}
```

Detection: if the body has a `data` key that is an object and a `meta` key, treat as envelope. Otherwise, treat entire body as `data`.

### Integration scenarios

| Scenario | How tracing works |
|----------|-------------------|
| **Web/mobile app** | App generates `message_id` per request. Uses `correlation_id` for multi-step flows (onboarding, booking). |
| **Partner EMR** | Sends `source_system: "partner-emr"`, `message_id` from their system. H360 logs both for cross-system audit. |
| **FHIR gateway** | `correlation_id` maps to FHIR `Bundle.id`. `message_id` maps to individual resource operations. |
| **Webhook receiver** | H360 sends outbound webhooks with `message_id` + `correlation_id` so the receiver can trace back to the originating action. |
| **Retry / idempotency** | Client resends same `idempotency_key` after timeout. Server returns cached response, no duplicate processing. |

### Implementation (NestJS middleware + interceptor)

```typescript
// request-envelope.middleware.ts
@Injectable()
export class RequestEnvelopeMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    // Detect envelope vs flat body
    if (req.body?.data && typeof req.body.data === 'object' && req.body.meta) {
      req['envelope'] = req.body;
      req.body = req.body.data;         // controllers see flat data
    } else {
      req['envelope'] = {
        data: req.body,
        meta: {},
        extras: req.body?.extras || {},
      };
    }

    // Resolve tracing IDs (body meta → headers → auto-generate)
    const meta = req['envelope'].meta;
    req['tracing'] = {
      message_id: meta.message_id
        || req.headers['x-message-id']
        || randomUUID(),
      correlation_id: meta.correlation_id
        || req.headers['x-correlation-id']
        || meta.message_id
        || req.headers['x-message-id']
        || randomUUID(),
      source_system: meta.source_system
        || req.headers['x-source-system']
        || 'h360-api',
      locale: meta.locale
        || req.headers['accept-language']?.split(',')[0]
        || 'en',
      idempotency_key: meta.idempotency_key || null,
    };

    next();
  }
}
```

## Standard Response Envelope

**Every** H360 API response follows this structure:

```json
{
  "data": {},
  "meta": {},
  "extras": {}
}
```

### Why this envelope

| Layer | Purpose | Examples |
|-------|---------|---------|
| `data` | **Domain payload** — the resource(s) the client asked for | Organization object, list of plans, onboarding state |
| `meta` | **Operational context** — request-scoped information about the response itself | Pagination, timestamps, request_id, tenant scope, API version, warnings |
| `extras` | **Optional enrichment** — related data that is useful but not part of the core resource | Upgrade suggestions, audit trail id, FHIR references, action hints |

### Design rationale for healthcare

- **Clear contract boundary**: clients can rely on `data` alone; `meta`/`extras` are additive.
- **Client stability**: new fields in `meta`/`extras` never break clients that only read `data`.
- **Cross-cutting needs**: auditing, traceability, paging, consent, facility scope, schema versioning, warnings ("partial data"), integration status — all fit naturally outside `data`.
- **Standard alignment**: aligns with JSON:API, Google AIP, and FHIR OperationOutcome patterns.

### Standard Error Response

**Every** error response follows this **uniform structure**. The frontend can rely on a single interface to handle all errors consistently.

#### Error Envelope Structure

```typescript
// Frontend can use ONE interface for all errors
interface ApiError {
  data: null;                    // Always null on error
  meta: {
    request_id: string;          // Server-generated
    message_id: string;          // Echoed from request
    correlation_id: string;      // Echoed from request
    timestamp: string;           // ISO 8601
    status_code: number;         // HTTP status code (400, 401, 403, 404, 409, 422, 429, 500)
    error: string;               // HTTP error label ("Bad Request", "Not Found", etc.)
    error_code: string;          // Machine-readable code (VALIDATION_ERROR, CLINIC_NOT_FOUND, etc.)
    message: string;             // Human-readable message (localized per request locale)
  };
  extras: {
    errors: FieldError[];        // Always present (empty array if no field-level errors)
    context: object | null;      // Domain-specific context (over-limit details, conflict info, etc.)
    related_links: object | null;// Helpful next actions
  };
}

interface FieldError {
  field: string;                 // Dot-notation path: "data.email", "data.operating_hours.monday"
  code: string;                  // Machine-readable: "REQUIRED", "INVALID_FORMAT", "TOO_LONG", etc.
  message: string;               // Human-readable (localized): "Must be a valid email address"
  rejected_value?: any;          // The value that was rejected (omitted for security-sensitive fields)
}
```

#### Field Error Codes (standard across all endpoints)

| Code | Meaning | Example message |
|------|---------|-----------------|
| `REQUIRED` | Field is missing | "This field is required" |
| `INVALID_FORMAT` | Value format is wrong | "Must be a valid email address" |
| `INVALID_TYPE` | Wrong data type | "Expected string, got number" |
| `TOO_SHORT` | Below minimum length | "Must be at least 2 characters" |
| `TOO_LONG` | Above maximum length | "Must be at most 150 characters" |
| `TOO_SMALL` | Below minimum value | "Must be at least 1" |
| `TOO_LARGE` | Above maximum value | "Must be at most 100" |
| `INVALID_ENUM` | Not in allowed values | "Must be one of: owner, manager, authorized_representative" |
| `INVALID_UUID` | Not a valid UUID | "Must be a valid UUID" |
| `INVALID_DATE` | Not a valid date | "Must be a valid ISO 8601 date" |
| `INVALID_PHONE` | Not E.164 format | "Must be a valid phone number in E.164 format" |
| `INVALID_URL` | Not a valid URL | "Must be a valid URL" |
| `NOT_UNIQUE` | Value already exists | "This email is already registered" |
| `NOT_FOUND` | Referenced resource missing | "Plan with this ID does not exist" |
| `FUTURE_DATE_REQUIRED` | Date must be in the future | "Must be a future date" |
| `PAST_DATE_REQUIRED` | Date must be in the past | "Must be a past date" |
| `OUT_OF_RANGE` | Value outside allowed range | "Must be between 1 and 100" |

#### Frontend Handling Guide

The uniform structure means frontend needs only **one error handler**:

```typescript
// Single handler for ALL API errors
function handleApiError(response: ApiError) {
  const { meta, extras } = response;

  // 1. Field-level errors → show inline on form fields
  if (extras.errors.length > 0) {
    const fieldErrors: Record<string, string> = {};
    for (const err of extras.errors) {
      // Strip "data." prefix for form field mapping
      const fieldName = err.field.replace(/^data\./, '');
      fieldErrors[fieldName] = err.message;
    }
    setFormErrors(fieldErrors);  // Maps directly to form field names
    return;
  }

  // 2. Business/domain errors → show as toast or banner
  showToast({
    type: meta.status_code >= 500 ? 'error' : 'warning',
    title: meta.error,
    message: meta.message,
    code: meta.error_code,       // For conditional UI (e.g., show upgrade CTA on PLAN_LIMIT_EXCEEDED)
    context: extras.context,     // For rich error display (e.g., show over-limit table)
  });

  // 3. Auth errors → redirect
  if (meta.status_code === 401) {
    redirectToLogin();
  }
}
```

# Section 1 — Tenancy, Accounts, Onboarding & Plans

> **FRs:** FR-001 through FR-007

## 1.0 Overview

This module handles tenant isolation, multi-branch organizations, subscription plans, guided onboarding, and initial data import. It provides the foundational structure on which all other H360 modules operate.

### Key Concepts

| Concept | Description |
|---------|-------------|
| **Organization** | A legal entity (clinic group, health network) that owns one or more clinics |
| **Tenant (Clinic)** | An individual clinic/branch — the primary unit of data isolation |
| **Plan** | A subscription tier defining feature access, limits, and pricing |
| **Subscription** | A clinic's active plan binding (plan + billing cycle + status) |
| **Onboarding** | A step-by-step wizard guiding a new clinic through setup |
| **Checklist** | Role-specific task list shown post-onboarding for adoption guidance |

# Section 2 — Clinic Directory & "Claim Your Clinic"

> **FRs covered:** FR-010, FR-011, FR-012, FR-013, FR-014, FR-015, FR-016, FR-017, FR-018
> **Priority:** P0 (6 FRs) + P1 (3 FRs)

---

## 2.0 Overview

The Clinic Directory is the **public-facing gateway** to H360 — a searchable, SEO-friendly catalog of clinics that patients use to find care. Clinics appear in the directory as either **claimed** (verified owner manages the profile) or **unclaimed** (pre-populated data, awaiting verification).

The "Claim Your Clinic" workflow allows clinic owners to verify ownership via OTP, then seamlessly transition into onboarding (Section 1.5) and an optional trial (Section 1.4).

**Key flows:**
1. **Patient → Directory** — Search, browse, view profile, book or record intent
2. **Clinic Owner → Claim** — Find unclaimed profile → OTP verify → onboarding → active
3. **Platform Admin → Outreach** — Monitor booking attempts on unclaimed profiles → trigger outreach
4. **Platform Admin → Quality** — Review corrections, opt-outs, featured listings

---

## 2.1 Data Models

### Clinic (extended fields for directory)

> The core `Clinic` entity is defined in Section 1. The following **directory-specific fields** extend it.

| Column | Type | Default | Description |
|--------|------|---------|-------------|
| `claim_status` | ENUM | `unclaimed` | `unclaimed`, `pending_verification`, `under_review`, `claimed`, `rejected` |
| `claimed_by` | UUID (FK → users) | NULL | User who successfully claimed the clinic |
| `claimed_at` | TIMESTAMPTZ | NULL | When the claim was approved |
| `visibility` | ENUM | `public` | `public`, `unlisted`, `private` |
| `seo_slug` | VARCHAR(200) | NULL | URL-friendly slug (auto-generated from name + city, editable) |
| `seo_title` | VARCHAR(160) | NULL | Custom meta title for search engines |

# Section 7 — Staff, Roles & Permissions

> **FRs covered:** FR-030, FR-031, FR-032, FR-033
> **Priority:** P0

## 7.0 Overview

This module handles authentication, user/employee lifecycle management, departments, user preferences, and the role-based access control (RBAC) system. It provides identity, authorization, and organizational structure on which all other H360 modules depend.

### Key Concepts

| Concept | Description |
|---------|-------------|
| **User** | A login identity (`users` table) — holds credentials, email, user_type |
| **Employee** | An employee profile linked to a User — holds role, clinic, department, personal info |
| **Role** | An ISD role name (`SYSTEM`, `ORG_OWNER`, `ADMIN`, `MANAGER`, `STAFF`, `DOCTOR`, `PATIENT`) mapped to granular `UserRole` enum values |
| **Permission** | A `resource:action` string (e.g., `patients:read`, `appointments:write`) assigned per role |
| **Department** | A clinic-scoped organizational unit for grouping employees |
| **User Preferences** | Per-user settings (theme, language, date/time format, notification preferences) |

### Role Hierarchy

```
SYSTEM          — Platform super-admin, full access to all resources
  └── ORG_OWNER — Organization-level admin, scoped to own organization
       └── ADMIN    — Clinic-level admin, full access within their clinic
            └── MANAGER   — Clinic manager, most operational permissions
                 ├── DOCTOR — Healthcare provider, clinical permissions
                 └── STAFF  — General staff (receptionist, nurse, lab tech, etc.)
                      └── PATIENT — Patient self-service only
```

### ISD Role → Internal Role Mapping

| ISD Role | Internal `UserRole` Values |
|----------|---------------------------|
| `SYSTEM` | Environment-based user (`user_type = 'SYSTEM'`, `permissions = 'ALL'`) |
| `ORG_OWNER` | `OrgOwner` |
| `ADMIN` | `Admin` |
| `MANAGER` | `Manager` |
| `SUPERVISOR` | `Supervisor` |
| `DOCTOR` | `Doctor` |
| `STAFF` | `Receptionist`, `Operator`, `Nurse`, `Nurse Assistant`, `Medical Assistant`, `Lab Technician`, `Radiologist`, `Radiology Technician`, `Physiotherapist`, `Pharmacist`, `Pharmacy Technician`, `HR`, `Accountant`, `Accounting Assistant`, `Stock Manager`, `Stock Assistant`, `IT Support`, `Security`, `Cleaner`, `Maintenance`, `Driver` |
| `PATIENT` | Patient user (`user_type = 'PATIENT'`) |

### Permission Model

Permissions use `resource:action` strings. `Admin` receives a wildcard `['*']` granting all permissions.

| Role | Key Permissions |
|------|----------------|
| **Admin** | `*` (all) |
| **Manager** | `patients:read/write`, `appointments:read/write`, `employees:read/write`, `clinics:read/write`, `services:read/write`, `doctors:read/write`, `slots:read/write`, `queue:read/write`, `reports:read`, `billing:read/write`, `activity-logs:read`, `notifications:read/write` |
| **Supervisor** | Same as Manager minus `billing:write`, `employees:write` |
| **Doctor** | `patients:read/write`, `appointments:read/write`, `services:read`, `slots:read/write`, `queue:read/write`, `medical-records:read/write`, `prescriptions:read/write`, `notifications:read` |
| **Nurse** | `patients:read/write`, `appointments:read`, `queue:read/write`, `medical-records:read/write`, `notifications:read` |
| **Receptionist** | `patients:read/write`, `appointments:read/write`, `queue:read/write`, `notifications:read` |

## 7.6 System Admins (FR-034)

System admins are platform-level super-users (`user_type = 'SYSTEM'`) stored in the database. The initial system admin is bootstrapped via environment variables (`SYSTEM_USER_EMAIL` / `SYSTEM_USER_PASSWORD`). Additional system admins are created via this API.

All endpoints require **SYSTEM** role.

### `POST /api/system-admins` — Create System Admin

> **Auth:** `SYSTEM`
> **Activity Log:** CREATE on User

**Request Body**
```json
{
  "data": {
    "email": "admin2@h360.system",
    "password": "SecurePass123!",
    "name": "Admin Two"
  },
  "meta": {
    "message_id": "msg_sys-admin-001",
    "source_system": "h360-web"
  },
  "extras": {}
}
```

| Field | Type | Required | Validation |
|-------|------|----------|------------|
| `data.email` | string | **Yes** | Valid email, max 255, unique across all users |
| `data.password` | string | **Yes** | Min 8, max 100 |
| `data.name` | string | No | Max 150 |

**Response `201 Created`**
```json
{
  "data": {
    "id": "uuid",
    "email": "admin2@h360.system",
    "name": "Admin Two",
    "is_active": true,
    "last_login": null,
    "created_at": "2026-03-07T14:00:00Z",
    "updated_at": "2026-03-07T14:00:00Z"
  },
  "meta": { "request_id": "req_abc123", "timestamp": "2026-03-07T14:00:00Z" },
  "extras": {}
}
```

**Errors**

| Code | Error Code | Condition |
|------|-----------|-----------|
| `409` | `EMAIL_EXISTS` | Email already registered |
